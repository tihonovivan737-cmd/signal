# Проектирование и проверка

## Задача

Хранить обращения пользователей, группировать их по характеру проблемы и давать сотруднику поддержки инструменты для анализа накопленных данных. Локальный ИИ должен участвовать в реальной работе сервиса, а не быть декоративным элементом интерфейса.

## Основные сценарии

1. Оператор добавляет обращение, при необходимости запускает ИИ-анализ и открывает карточку.
2. Оператор находит обращения по теме, тексту, автору, периоду, категории и статусу, исправляет классификацию и меняет статус.
3. Аналитик изучает динамику, доли категорий, рейтинг причин и изменение относительно предыдущего периода.
4. Аналитик формирует текстовый отчёт и выгружает статистику или обращения.
5. Пользователь выбирает установленную модель ИИ и видит состояние соединения.

## Решения по архитектуре

- React и Express позволяют использовать один язык на клиенте и сервере. Vite собирает интерфейс, который в рабочем режиме раздаёт сам Express.
- SQLite удобна для локального запуска и переносимости. Используется встроенный модуль Node.js 24, без сборки сторонних нативных зависимостей.
- Категории и причины заданы справочниками: это делает аналитику сопоставимой и ограничивает произвольные ответы модели.
- Теги нормализованы, уникальны и связаны с обращениями отдельной таблицей. Свободный текст не исполняется и отображается средствами React с экранированием.
- ИИ вызывается на сервере по HTTP, получает JSON-схему и ограниченный контекст. Обязательная проверка ответа предшествует записи в базу.
- Создание обращения не зависит от времени ответа модели. Автоанализ запускается отдельным запросом после успешного сохранения.
- Версии записей защищают ручные правки от конфликтов и запоздавших ответов модели.
- Уведомления о росте основаны на явных порогах; статистика не зависит от выводов ИИ.

## Этапы реализации

| Этап | Результат |

| Требования | Основные сценарии и границы локальной версии |

| Интерфейс | Адаптивные страницы и карточки, графики и состояния ошибок |
| Тестирование | Изолированные API-тесты, браузерные сценарии и проверка реальной модели |
| Документация | Запуск, формулы, API, ограничения, описание для сдачи |

## Проверки качества

Автоматизированные серверные проверки:

- Создание, чтение, классификация, редактирование и история.
- Сохранение SQLite после закрытия и повторного открытия.
- Нормализация тегов и защита от устаревших правок.
- Поиск на русском, комбинированные фильтры, экранирование `%`, `_` и SQL-подобного текста.
- Некорректные поля, несуществующие ID, невозможные даты, лимиты пагинации.
- Запрет изменяющих запросов с чужого сайта и с неправильным типом содержимого.
- Точные границы дней, нулевые дни, сравнение периодов, среднее время и пороги роста.
- Валидация ИИ, резервная категоризация, маскирование email и номеров.
- Текстовая сводка и отсутствие контактных полей в запросе отчёта.
- CSV с фильтрами, кавычками, переносами строк и защитой от формул.
- Конфликт между ручной правкой и длительным анализом.

Браузерные проверки:

- Главный экран, данные и графики без ошибок JavaScript.
- Создание обращения, поиск кириллицей, правка статуса и тегов, проверка после перезагрузки.
- Фильтрация, пустое состояние, скачивание CSV, резервный отчёт.
- Автоматический резервный анализ без потери обращения.
- Экран 390 пикселей, отсутствие горизонтального переполнения страницы, мобильная навигация, закрытие формы клавишей Escape.

Скрипт `scripts/check-ai.mjs` отдельно проверяет реальную категоризацию и отчёт через установленную модель. Результаты не попадают в рабочую базу.

## Дальнейшее развитие

Роли операторов и аналитиков, внешние каналы поступления обращений, PostgreSQL и SQL-агрегации для больших объёмов, надёжная очередь анализа, журнал аналитических отчётов и экспорт XLSX. Эти функции не заявляются как реализованные.
